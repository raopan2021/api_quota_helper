# 01-微前端概念与优势

## 什么是微前端？

微前端（Micro Frontends）是一种将前端应用拆分为多个可独立开发、测试、部署的子应用的架构风格。它借鉴了微服务的思想，让前端应用也能实现模块化、独立化和自治化。

### 核心思想

```
传统前端架构（巨石应用）：
┌─────────────────────────────────────────┐
│              单体前端应用                 │
├──────────┬──────────┬──────────────────┤
│  导航栏   │  侧边栏   │      主内容区     │
├──────────┴──────────┴──────────────────┤
│              共享组件库                  │
├─────────────────────────────────────────┤
│              共享状态管理                 │
├─────────────────────────────────────────┤
│              路由系统                    │
└─────────────────────────────────────────┘

微前端架构：
┌─────────┐  ┌─────────┐  ┌─────────┐  ┌─────────┐
│ 主应用   │  │ 子应用A  │  │ 子应用B  │  │ 子应用C  │
│ (容器)   │  │ (订单)   │  │ (用户)   │  │ (商品)   │
└────┬────┘ ─────────┘  ─────────┘  ─────────┘
     │
     ↓
┌─────────────────────────────────────────┐
│           独立部署，独立版本              │
│         独立团队维护，技术栈不限          │
└─────────────────────────────────────────┘
```

## 微前端的核心价值

### 1. 独立部署（Independent Deployment）

每个子应用可以独立打包、部署，不影响其他子应用。

```bash
# 子应用A 部署
cd app-order && npm run build && npm run deploy

# 子应用B 部署
cd app-user && npm run build && npm run deploy

# 主应用部署
cd main-app && npm run build && npm run deploy

# 三个应用可以同一天部署多次，互不影响
```

### 2. 独立开发（Independent Development）

不同团队可以独立开发各自负责的子应用。

```
团队结构：
├── 订单团队（负责 order 子应用）
│   ├── 技术栈：React
│   ├── 代码库：order-app
│   └── 发布节奏：每周一发布
│
├── 用户团队（负责 user 子应用）
│   ├── 技术栈：Vue
│   ├── 代码库：user-app
│   └── 发布节奏：随时发布
│
└── 主应用团队（负责主应用容器）
    ├── 技术栈：Vue
    ├── 代码库：main-app
    └── 发布节奏：跟随整体发布
```

### 3. 技术栈无关（Technology Agnostic）

主应用和子应用可以使用不同的技术栈：

```javascript
// 主应用（Vue 3）
import { createApp } from 'vue';
const app = createApp({});

// 子应用A（React 18）
import React from 'react';
import { createRoot } from 'react-dom/client';

// 子应用B（Svelte）
import App from './App.svelte';

// 子应用C（Angular）
import { bootstrapApplication } from '@angular/platform-browser';
```

### 4. 增量升级（Incremental Upgrades）

可以逐步将老旧应用升级，而不是一次性重写：

```
阶段1：引入微前端架构
旧系统 + 新子应用（部分功能使用微前端）

阶段2：迁移核心模块
逐步将旧系统功能迁移到新子应用

阶段3：完全升级
旧系统完全替换，新架构全面上线
```

### 5. 沙箱隔离（Sandbox Isolation）

每个子应用运行在独立的 JavaScript 沙箱中，不会相互污染：

```javascript
// 子应用A 的全局变量
window.userName = 'Alice';  // 只在子应用A内有效

// 子应用B 无法访问
console.log(window.userName);  // undefined
```

## 微前端的实现方式

### 1. 微件化（Micro Widget）

将子应用打包成 Web Component，只包含 UI 组件。

```
优点：标准化、自包含
缺点：样式隔离困难、性能开销
```

### 2. 框架无关的运行时（Framework Agnostic Runtime）

通过动态加载脚本的方式运行子应用，如 qiankun。

```
优点：技术栈无关、样式隔离好
缺点：需要额外的运行时库
```

### 3. 模块联邦（Module Federation）

Webpack 5 内置的模块共享方案，如 Webpack Module Federation。

```
优点：原生支持、性能好
缺点：需要 Webpack 5、部分浏览器兼容问题
```

## 微前端的核心机制

### 应用注册与生命周期

```javascript
// qiankun 示例
import { registerMicroApps, start } from 'qiankun';

// 注册子应用
registerMicroApps([
    {
        name: 'order-app',                    // 子应用名称
        entry: '//localhost:8081',             // 子应用入口
        container: '#micro-container',        // 挂载容器
        activeRule: '/order',                 // 激活规则
        // 生命周期钩子
        loader: (loading) => console.log(loading),
        beforeMount: [() => console.log('before mount')],
        afterMount: [() => console.log('after mount')],
        beforeUnmount: [() => console.log('before unmount')],
        afterUnmount: [() => console.log('after unmount')],
    },
]);

// 启动微前端
start();
```

### 通信机制

子应用之间通过事件或共享状态进行通信：

```javascript
// 方式1：基于 initGlobalState（qiankun）
// 主应用
import { initGlobalState } from 'qiankun';

const actions = initGlobalState({ user: null });

actions.onGlobalStateChange((state, prev) => {
    console.log('主应用监听到变化：', state);
});

actions.setGlobalState({ user: { name: '张三' } });

// 子应用
import { initGlobalState } from 'qiankun';

const actions = initGlobalState({ user: null });

actions.onGlobalStateChange((state, prev) => {
    console.log('子应用监听到变化：', state);
});
```

```javascript
// 方式2：基于 Window 的事件通信
// 发送方
window.dispatchEvent(new CustomEvent('user-login', {
    detail: { userId: 123, name: '张三' }
}));

// 接收方
window.addEventListener('user-login', (e) => {
    console.log('收到用户登录事件：', e.detail);
});
```

### 样式隔离

微前端需要处理子应用之间的样式冲突：

```css
/* 子应用A */
.order-page { background: red; }

/* 子应用B */
.order-page { background: blue; }  /* 不会覆盖子应用A */
```

常见的样式隔离方案：

| 方案 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| CSS Modules | 生成唯一的类名 | 成熟稳定 | 需要构建工具支持 |
| Shadow DOM | 浏览器原生隔离 | 原生支持 | 样式复用困难 |
| BEM 命名 | 约定命名规范 | 简单 | 依赖团队规范 |
| CSS-in-JS | 运行时生成唯一类名 | 灵活 | 运行时开销 |

## 什么时候使用微前端？

### 适合使用微前端的场景

1. **大型 B 端管理系统**
   - 10+ 个独立模块
   - 多个团队并行开发
   - 需要独立发布能力

2. **老旧项目升级**
   - 巨石应用难以维护
   - 需要逐步迁移
   - 不能影响现有业务

3. **多产品线复用**
   - 多套产品共用基础组件
   - 子应用可被不同主应用引用
   - 需要独立版本管理

### 不适合使用微前端的场景

1. **小型简单应用**
   - 功能单一，代码量少
   - 团队规模小（1-3人）
   - 快速迭代优先

2. **需要高频跨应用交互**
   - 子应用之间高度耦合
   - 频繁共享状态
   - 通信开销反而更大

3. **SEO 优先的应用**
   - 需要服务端渲染
   - 首屏性能要求高
   - 爬虫依赖 DOM 结构

## 微前端 vs 单体应用

| 维度 | 微前端 | 单体应用 |
|------|--------|----------|
| 部署 | 各子应用独立部署 | 统一部署 |
| 开发 | 多团队并行 | 团队协作 |
| 技术栈 | 可异构 | 需统一 |
| 性能 | 首屏加载较慢 | 首屏加载较快 |
| 复杂度 | 较高 | 较低 |
| 维护成本 | 需要额外的运行时 | 较低 |
| 沙箱隔离 | 支持 | 不支持 |
| 版本管理 | 各子应用独立版本 | 统一版本 |
